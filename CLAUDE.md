# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A standalone 1:1 direct-messaging app (phase 5 of a larger plan — see below). Any
registered user can self-signup (email+password or Google) and message another
registered user, but only once they're mutual friends via an add-by-ID
request/accept flow; there are no roles, groups, or admin overrides. The app is
installable (PWA) and can send Web Push notifications for messages that arrive
while it isn't open. Messages can also be backed up to each user's own Google
Drive, with the server's own copy pruned once every participant has archived
it. See `README.md` for setup, the API endpoint table, and available scripts.

- **Backend**: Node.js + Express 5 (`src/`), Prisma ORM + PostgreSQL via `@prisma/adapter-pg` (`prisma/`)
- **Frontend**: React + Vite SPA (`web/`)
- **Auth**: JWT (`Authorization: Bearer <token>`) — email + password self-signup, or Google OAuth
- **Tests**: `node:test` + Supertest (`tests/`) against a dedicated PostgreSQL test database

## History: ported from a POS/inventory app

This code started as a chat feature bolted onto an existing inventory/POS system
(`sandsd01/sandsd01`), reusing that app's `User`/auth. Once the owner decided chat
should be a public, standalone product with self-signup, it was split out into this
repository — a chat app and a shop's back office are different products with
different users and shouldn't share deploys, roles, or a database. This repo is the
result of that split: the chat feature carried over essentially unchanged (routes,
schema, SSE design), while every shop-specific concept (roles, branches, sales,
inventory) was dropped rather than ported. If you find a comment or pattern that
seems to assume "staff vs admin" and it's gone, that's why — there is no role
system in this app yet (see Roadmap below for when one returns, and why it will
mean something different this time).

## Commands

```bash
npm install                 # also runs `prisma generate` via postinstall
npx prisma migrate deploy   # apply prisma/migrations to the database in DATABASE_URL
npm run seed                # seed two local dev accounts
npm run dev                 # run the backend with auto-restart (http://localhost:3000)
npm test                    # migrate the test database, then run the full backend suite
```

To run a single backend test file: `DATABASE_URL="$TEST_DATABASE_URL" JWT_SECRET="test-secret" NODE_ENV="test" node --test tests/chat.test.js` (run `npm run test:migrate` first). `tests/helpers/db.js` defaults `DATABASE_URL` to the local `chatapp_test` database when it isn't already set.

Frontend (`cd web` first):

```bash
npm install
npm run dev     # http://localhost:5173, proxies /api/* to the backend
npm run build   # production build, also run in CI
```

## Architecture

- `src/app.js` wires up Express routes and middleware; `src/server.js` is the actual process entry point (reads env, calls `app.listen`) — tests import `app.js` directly and never start a real listener. All API routers are mounted under `/api`, because `src/app.js` also serves the built SPA from `web/dist` when it exists: a client-side route like `/chat/42` would otherwise resolve to the API router and return JSON to a browser asking for a page. The SPA fallback serves `index.html` for any GET that isn't under `/api` or `/health`, so an unknown API path still returns the JSON 404 rather than HTML a `fetch()` caller can't parse. `web/vite.config.js` proxies `/api` **without rewriting it**, so dev and a single-origin production deploy see identical paths — don't reintroduce a prefix-stripping rewrite. `helmet` sets the security headers; CORS is off by default in production and enabled only via `CORS_ORIGIN` for a separately-hosted frontend. `TRUST_PROXY` must be set when running behind a load balancer, or `express-rate-limit` buckets every client under the proxy's IP.
- `src/middleware/auth.js`: `authenticate` verifies the JWT and attaches `req.user`; `requireRole(...roles)` exists but is currently unused (no route calls it) — there is no role system yet. It's kept rather than deleted because Roadmap #3 will need exactly this pattern if a role field is ever added; don't reach for it before that.
- `prisma/client.js` is the single shared Prisma Client instance (constructed with the pg driver adapter; it throws at require time if `DATABASE_URL` is unset) — routes and scripts require this rather than instantiating their own client.
- Chat (`src/routes/chat.js`, mounted at `/api/chat`, `Conversation` + `Message`) is 1:1 direct messaging. A conversation stores its pair as `userAId`/`userBId` **canonically ordered by the backend** (`userAId = Math.min(me, target)`, `userBId = Math.max(...)`), which is what turns `@@unique([userAId, userBId])` into an idempotent find-or-create — `POST /conversations` returns `201` on create and `200` on the existing row no matter who initiates — with no participants join table to reason about. The database does **not** enforce that ordering, so any new write path must canonicalise the pair itself or it will create a duplicate mirrored row. Unread state is two nullable timestamps on the conversation (`userALastReadAt`/`userBLastReadAt`, bumped by `POST /conversations/:id/read`) with `unreadCount` counted from them, deliberately instead of a per-message read-receipts table: "never read" is simply a null, and a reader only ever writes their own column. `GET /conversations/:id/messages` pages newest-first on a `before` message-id cursor, fetching `limit + 1` rows to derive `hasMore` without a second count query.
- Live delivery is SSE: `POST /stream-ticket` mints a single-use, 30-second ticket kept in process memory, and `GET /api/chat/stream?ticket=` is registered **before `router.use(authenticate)`** on purpose — `EventSource` cannot send an `Authorization` header, and putting the real JWT in a query string would leak it into access logs and `Referer`, so don't "tidy" the stream back under the JWT middleware. `src/lib/chatBus.js` is a plain in-process `EventEmitter`, correct only while the app runs as exactly one instance; running multiple instances (or cluster mode) needs every publish fanned out via Redis pub/sub or equivalent — it does not do that today. See the `SINGLE INSTANCE ONLY` comment block at the top of `render.yaml` before ever adding a `numInstances`/`scaling` key.
- Three privacy choices are intentional, not oversights: a non-participant gets **404, not 403** on any conversation-scoped route, there is **no admin override** for reading other people's DMs (there is no admin at all), and message bodies are **never** logged anywhere — this app has no audit-log table, on purpose, because chat content doesn't belong in one.
- `DELETE /users/me` 409s if the caller is in any conversation or has sent any message, the same "refuse rather than orphan" pattern you'd see guarding any FK-linked delete — a DM thread has no "detach and keep going" story. There is no route to delete *another* user's account; the only actor here is the account itself.
- `POST /auth/signup` (`src/routes/auth.js`) is a deliberately bare email+password self-signup — no email verification, no CAPTCHA — because its only job right now is giving the friend system real accounts to test against. It is explicitly **not** meant to be the production signup flow; see Roadmap #1. It's also the only place a brand-new account gets a `publicId` outside of `prisma/seed.js`, both going through `src/lib/publicId.js#createUserWithUniquePublicId` so the generation + collision-retry logic isn't duplicated.
- **Friends** (`src/routes/friends.js`, mounted at `/api/friends`, `User.publicId` + `Friendship`): you must be mutual, accepted friends before you can message someone at all. `User.publicId` is a short random code (`src/lib/publicId.js`, alphabet excludes `0/O/1/I/L`), generated once at signup and handed out instead of the numeric `id` specifically because the numeric id is sequential and enumerable (id=5 existing tells you id=1..4 probably do too) — a public "add me" code must not leak that. `Friendship` reuses `Conversation`'s canonical-pair trick (`userAId = min`, `userBId = max`, `@@unique([userAId, userBId])`) so there's one row per pair regardless of who acts first, plus a `status` (`pending`/`accepted`/`declined` never persists — see below — /`blocked`) and a `requestedById` recording who actually initiated (the one thing the canonical pair alone can't tell you). A **mutual request auto-accepts**: if B requests A while A's request to B is still pending, `POST /friends/requests` flips straight to `accepted` instead of leaving two pending rows each side has to separately act on — this mirrors how "you both hit add" behaves in most consumer apps. Declining or cancelling a request **deletes the row** rather than storing `declined`, on purpose, so the same two people can try again later without a stale row in the way; only `blocked` persists (it's an upsert to the same canonical row, so blocking overwrites any prior pending/accepted state, and only the user who set it can clear it via `POST /:userId/unblock`). `src/routes/chat.js` imports `areFriends()` from here and checks it both at `POST /conversations` (403 if not friends) and again at `POST /conversations/:id/messages` (re-checked at send time, not just conversation-creation time, so unfriending after the fact blocks new sends but old history stays readable) — deliberately not checked on the read routes. The old `GET /chat/users?q=` fuzzy directory search (find anyone by typing part of their name/email) was removed entirely rather than kept alongside this: once signup is public, letting any account browse every other registered user by name is the same privacy problem the public/numeric-id split above exists to avoid. `GET /friends/lookup?publicId=` is the only way to find someone now, and only by the exact code they handed you.
- **PWA + Web Push** (`web/public/manifest.webmanifest`, `web/public/sw.js`, `web/public/icons/`, `src/routes/push.js` mounted at `/api/push`, `src/lib/push.js`, `PushSubscription`): `web/src/main.jsx` registers the service worker unconditionally on load, which is what makes the app installable — that part needs no permission and no login. Actually *subscribing* to push is separate and gated behind an explicit user gesture on the Account page (`web/src/hooks/usePushSubscription.js`), because `Notification.requestPermission()` must be called from one. VAPID keys are self-generated (`npx web-push generate-vapid-keys`, no external account) and optional at the `src/lib/email.js`/Resend pattern: `src/lib/push.js#sendPushToUser` no-ops (logged, not thrown) if `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` aren't set, so the app runs fine with push simply unavailable. A subscription is per-browser (`endpoint` is globally unique, upserted on re-subscribe), so one account can have several. `POST /chat/conversations/:id/messages` fires a push at the recipient **only when `chatBus.hasSubscribers(otherUserId)` is false** — someone with a live SSE stream open already gets the message that way, and pushing them too would be a redundant OS notification for the same event; this also means the "who's connected" check `chatBus.js` gained (`hasSubscribers`, a thin wrapper over `EventEmitter#listenerCount`) inherits its single-process caveat — on more than one instance it only sees this process's subscribers. The push call is fired without `await`ing it (`.then(...).catch(console.error)`), because a slow or failing push must never delay the response the sender is waiting on. `sendPushToUser` deletes a subscription outright on a `404`/`410` from the push service (the browser itself revoked it) but leaves it alone and just logs on any other error, so a transient failure doesn't lose a working subscription. Friend-request notifications (`src/routes/friends.js#notify`) are simpler but *not* symmetric with chat's gating: they fire unconditionally rather than checking `chatBus.hasSubscribers`, because that would only tell you the recipient has a *chat* stream open, not that they've seen the request — `FriendsContext` has no live stream of its own to check against (see Roadmap). **iOS note**: Safari only supports Web Push for a PWA actually added to the Home Screen (16.4+); granting permission from a normal Safari tab does nothing there.
- **Google sign-in** (`src/routes/auth.js`, `GET /auth/google` + `/auth/google/callback` + `POST /auth/google/exchange`) is the Authorization Code flow via `google-auth-library`'s `OAuth2Client`, and it's optional the same way `src/lib/email.js`/`src/lib/push.js` are: a module-level `googleConfigured = Boolean(GOOGLE_CLIENT_ID && GOOGLE_CLIENT_SECRET && GOOGLE_REDIRECT_URI)` gate makes `GET /auth/google` `503` cleanly instead of constructing a client with `undefined` credentials, so the app runs fine with Google sign-in simply unavailable. CSRF protection is a `state` value round-tripped through an httpOnly, `sameSite=lax` cookie (`g_oauth_state`, 5-minute TTL) rather than server-side session storage, since this app has no session store at all — bearer JWT only. Handing the browser a real JWT after Google's redirect reuses the **exact same single-use-ticket pattern** as the SSE stream's `POST /stream-ticket` (a `Map` of random-ticket → payload, 30-second TTL, consumed exactly once): a full-page redirect can't receive a JSON response, and a JWT sitting in a URL would leak into access logs, browser history, and `Referer` headers, so `GET /auth/google/callback` mints a short-lived ticket, redirects to `${APP_URL}/oauth-callback?ticket=`, and `POST /auth/google/exchange` trades it for the real `{ token, user }` — mirroring the stream ticket's reasoning exactly rather than inventing a second pattern for the same problem. Sign-in resolves to a user by `googleId` (Google's stable `sub` claim) first; if that misses but a `User` row already exists with the same **Google-verified** (`email_verified: true`) email, it auto-links by setting `googleId` on that row rather than creating a second account — one person should get one account regardless of which method they used to sign in, and only a Google-*verified* email is trusted enough to link onto an existing password account. `User.passwordHash` is nullable for exactly this reason (a Google-only account never sets one); `POST /auth/login` and `PATCH /auth/password` both check for `null` before calling `bcrypt.compare` (which throws on a null comparand) and return a clear "this account signs in with Google" error instead of a 500. Every failure path (`invalid_state`, `email_not_verified`, `google_exchange_failed`, `google_not_configured`) redirects to `${APP_URL}/login?error=<reason>` rather than rendering an error page server-side, keeping the SPA in control of all UI.
- **Google Drive backup** (`src/routes/drive.js` mounted at `/api/drive`, `src/lib/drive.js`, `src/lib/crypto.js`, `User.driveRefreshTokenEnc`/`driveConnectedAt`/`driveFolderId`, `DriveArchiveFile`) is a *separate* OAuth consent flow from Google sign-in, not a side effect of it — sign-in only ever requests `access_type: "online"` (a grant good for that one exchange, no refresh token), while backup needs `access_type: "offline"` + `prompt: "consent"` on the `drive.file` scope so the server gets a refresh token it can use unattended, later, on a schedule. Both reuse the same `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, but Google ties the requested scopes to the exact redirect URI that was authorized for them, so this flow needs its own `DRIVE_REDIRECT_URI`. Connecting is initiated from an *authenticated* `POST /drive/connect/start` (not a plain link, unlike `/auth/google`) specifically so the state map can record which user is connecting — `driveConnectStates: Map<state, {userId, expiresAt}>` — because the callback that completes the flow is a top-level redirect with no Authorization header to identify the caller from; the `g_drive_state` cookie is defense-in-depth on top of that, not the only thing tying the callback to the right account. The refresh token is encrypted at rest (`src/lib/crypto.js`, AES-256-GCM, key from `TOKEN_ENCRYPTION_KEY`) because unlike a JWT it doesn't expire on its own — a DB dump alone must not be enough to act as the user against their Drive. `driveConfigured` (in `src/lib/drive.js`) gates everything the same optional-service way as `email.js`/`push.js`/sign-in's `googleConfigured`: unset any of `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`/`DRIVE_REDIRECT_URI`/`TOKEN_ENCRYPTION_KEY` and the connect/sync routes `503` rather than the app crashing or half-working. `src/lib/drive.js` talks to the Drive v3 REST API directly via `fetch` rather than the `googleapis` package (a much heavier dependency for the handful of calls this needs: search/create a folder, create a file, download-then-reupload its content). Archiving is **server-driven**, not client-driven: `src/server.js` runs `runArchiveSweep()` on a cron (`DRIVE_SYNC_CRON`, default every 15 minutes) that walks every Drive-connected user, appends their unarchived messages into a per-conversation JSONL file inside a "Chat Backups" folder in *their own* Drive, and advances their `DriveArchiveFile.lastArchivedMessageId` watermark — this was a deliberate simplification over having each client sync its own copy: one writer per file means no multi-device conflict resolution to design, and archiving still happens for a user who's offline. `pruneArchivedMessages()` only deletes a `Message` once **every** participant of its conversation has a `DriveArchiveFile` row with a watermark at or past it — a conversation where the other side hasn't connected Drive at all never gets pruned, by construction (there's no row to check, so `archives.length < participantIds.length` and the loop skips it), which is the deliberate trade-off for never losing a message the other side can't see anywhere else yet. `POST /drive/disconnect` clears this user's own token and `DriveArchiveFile` rows but never touches the files already written into their Drive — those are theirs regardless of whether the app is still connected.
- Money/Decimal handling, S3-compatible upload storage, audit logging, VAT/tax, cash-shift reconciliation, and role-based access do **not** exist in this app — they were part of the shop app this was split from and were deliberately not carried over. If you're tempted to add one of these because it "seems missing," check the Roadmap below first; it's very likely out of scope rather than forgotten.

## Roadmap (not yet implemented)

These are planned next phases, mentioned here so their absence isn't mistaken for an oversight:

1. **Live friend-request updates.** `web/src/context/FriendsContext.jsx` only refetches on mount and after an action taken through it, so an incoming request or acceptance that happens while the tab is open and idle doesn't appear until something else triggers a refetch — push notifications for it now exist (see above), but there's no in-app live update to match chat's SSE stream. Folding friend events into the same stream (or giving Friends its own) is future work.
2. **Reading pruned history back out of Drive.** Once `pruneArchivedMessages()` deletes a message from Postgres, it only lives in each participant's own Drive file — there is no in-app "load older messages from Drive" for `GET /conversations/:id/messages` to fall back to, so very old history is effectively export-only (a user can open the JSONL file in Drive directly, but not scroll to it in the chat UI). Building that would mean the currently-logged-in user's own Drive access token being available live in-session (today it's only ever used server-side, briefly, during the cron sweep) and merging their Drive-backed pages with Postgres's live tail.
3. **A `role`/permission field on `User`.** Not needed yet — every account can do the same things in this app — but if any admin-style capability is ever added, it should be scoped to "what can this account do in *this* app," not resurrect the old shop app's admin/staff distinction.

## Conventions

- Backend and frontend are separate npm projects (root `package.json` vs `web/package.json`) with independent dependencies and CI jobs.
- Never commit `.env` (gitignored) — use `.env.example` as the template for required environment variables.
- New backend routes needing role restriction should reuse `requireRole` rather than checking `req.user.role` ad hoc, once a role field actually exists again (see Roadmap #3).
