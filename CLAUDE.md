# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A standalone 1:1 direct-messaging app (phase 5 of a larger plan — see below). Any
registered user can self-signup (email+password or Google) and message another
registered user, but only once they're mutual friends via an add-by-ID
request/accept flow, with live updates for both new messages and incoming
friend requests; there are no roles, groups, or admin overrides. The app is
installable (PWA) and can send Web Push notifications for messages that arrive
while it isn't open. Accounts carry a light profile — an avatar, a short
status line, and a point-in-time online indicator. See `README.md` for setup,
the API endpoint table, and available scripts.

- **Backend**: Node.js + Express 5 (`src/`), Prisma ORM + PostgreSQL via `@prisma/adapter-pg` (`prisma/`)
- **Frontend**: React + Vite SPA (`web/`)
- **Auth**: JWT (`Authorization: Bearer <token>`) — email + password self-signup, or Google OAuth
- **Tests**: `node:test` + Supertest (`tests/`) against a dedicated PostgreSQL test database

## History: ported from a POS/inventory app

This code started as a chat feature bolted onto an existing inventory/POS system
(`sandsd01/sandsd01`), reusing that app's `User`/auth. Once the owner decided chat
should be a public, standalone product with self-signup, it was split out into this
repository — a chat app and a shop's back office are different products with
different users and shouldn't share deploys, roles, or a database. This repo is the
result of that split: the chat feature carried over essentially unchanged (routes,
schema, SSE design), while every shop-specific concept (roles, branches, sales,
inventory) was dropped rather than ported. If you find a comment or pattern that
seems to assume "staff vs admin" and it's gone, that's why — there is no role
system in this app yet (see Roadmap below for when one returns, and why it will
mean something different this time).

## Commands

```bash
npm install                 # also runs `prisma generate` via postinstall
npx prisma migrate deploy   # apply prisma/migrations to the database in DATABASE_URL
npm run seed                # seed two local dev accounts
npm run dev                 # run the backend with auto-restart (http://localhost:3000)
npm test                    # migrate the test database, then run the full backend suite
```

To run a single backend test file: `DATABASE_URL="$TEST_DATABASE_URL" JWT_SECRET="test-secret" NODE_ENV="test" node --test tests/chat.test.js` (run `npm run test:migrate` first). `tests/helpers/db.js` defaults `DATABASE_URL` to the local `chatapp_test` database when it isn't already set.

Frontend (`cd web` first):

```bash
npm install
npm run dev     # http://localhost:5173, proxies /api/* to the backend
npm run build   # production build, also run in CI
```

## Architecture

- `src/app.js` wires up Express routes and middleware; `src/server.js` is the actual process entry point (reads env, calls `app.listen`) — tests import `app.js` directly and never start a real listener. All API routers are mounted under `/api`, because `src/app.js` also serves the built SPA from `web/dist` when it exists: a client-side route like `/chat/42` would otherwise resolve to the API router and return JSON to a browser asking for a page. The SPA fallback serves `index.html` for any GET that isn't under `/api` or `/health`, so an unknown API path still returns the JSON 404 rather than HTML a `fetch()` caller can't parse. `web/vite.config.js` proxies `/api` **without rewriting it**, so dev and a single-origin production deploy see identical paths — don't reintroduce a prefix-stripping rewrite. `helmet` sets the security headers; CORS is off by default in production and enabled only via `CORS_ORIGIN` for a separately-hosted frontend. `TRUST_PROXY` must be set when running behind a load balancer, or `express-rate-limit` buckets every client under the proxy's IP.
- `src/middleware/auth.js`: `authenticate` verifies the JWT and attaches `req.user`; `requireRole(...roles)` exists but is currently unused (no route calls it) — there is no role system yet. It's kept rather than deleted because the Roadmap's role item will need exactly this pattern if a role field is ever added; don't reach for it before that. `requireVerifiedEmail`, by contrast, *is* used (see `POST /friends/requests` below) — it re-queries `User.emailVerifiedAt` fresh on every call rather than trusting a claim baked into the JWT at sign-time, because verifying an email happens mid-session and a signed token has no way to un-stale itself.
- `prisma/client.js` is the single shared Prisma Client instance (constructed with the pg driver adapter; it throws at require time if `DATABASE_URL` is unset) — routes and scripts require this rather than instantiating their own client.
- Chat (`src/routes/chat.js`, mounted at `/api/chat`, `Conversation` + `Message`) is 1:1 direct messaging. A conversation stores its pair as `userAId`/`userBId` **canonically ordered by the backend** (`userAId = Math.min(me, target)`, `userBId = Math.max(...)`), which is what turns `@@unique([userAId, userBId])` into an idempotent find-or-create — `POST /conversations` returns `201` on create and `200` on the existing row no matter who initiates — with no participants join table to reason about. The database does **not** enforce that ordering, so any new write path must canonicalise the pair itself or it will create a duplicate mirrored row. Unread state is two nullable timestamps on the conversation (`userALastReadAt`/`userBLastReadAt`, bumped by `POST /conversations/:id/read`) with `unreadCount` counted from them, deliberately instead of a per-message read-receipts table: "never read" is simply a null, and a reader only ever writes their own column. `GET /conversations/:id/messages` pages newest-first on a `before` message-id cursor, fetching `limit + 1` rows to derive `hasMore` without a second count query.
- Live delivery is SSE: `POST /stream-ticket` mints a single-use, 30-second ticket kept in process memory, and `GET /api/chat/stream?ticket=` is registered **before `router.use(authenticate)`** on purpose — `EventSource` cannot send an `Authorization` header, and putting the real JWT in a query string would leak it into access logs and `Referer`, so don't "tidy" the stream back under the JWT middleware. `src/lib/chatBus.js` is a plain in-process `EventEmitter`, correct only while the app runs as exactly one instance; running multiple instances (or cluster mode) needs every publish fanned out via Redis pub/sub or equivalent — it does not do that today. See the `SINGLE INSTANCE ONLY` comment block at the top of `render.yaml` before ever adding a `numInstances`/`scaling` key.
- Three privacy choices are intentional, not oversights: a non-participant gets **404, not 403** on any conversation-scoped route, there is **no admin override** for reading other people's DMs (there is no admin at all), and message bodies are **never** logged anywhere — this app has no audit-log table, on purpose, because chat content doesn't belong in one.
- `DELETE /users/me` 409s if the caller is in any conversation or has sent any message, the same "refuse rather than orphan" pattern you'd see guarding any FK-linked delete — a DM thread has no "detach and keep going" story. There is no route to delete *another* user's account; the only actor here is the account itself.
- `POST /auth/signup` (`src/routes/auth.js`) is email+password self-signup, hardened two ways: an optional CAPTCHA check and a mandatory post-signup email verification step. It's also the only place a brand-new account gets a `publicId` outside of `prisma/seed.js`, both going through `src/lib/publicId.js#createUserWithUniquePublicId` so the generation + collision-retry logic isn't duplicated.
  - **CAPTCHA** (`src/lib/captcha.js`, Cloudflare Turnstile) is optional the same way Google sign-in/Web Push are: `captchaConfigured = Boolean(TURNSTILE_SECRET_KEY)`, and when it's false signup simply skips the check rather than 503ing or crashing. `TURNSTILE_SITE_KEY` isn't secret (it's meant to sit in the signup page's HTML) but is still served from `GET /auth/captcha-config` rather than baked into the frontend build via a Vite env var, the same reasoning as the VAPID public key being served from `GET /push/vapid-public-key` — one build works across every environment without a rebuild per deploy. `verifyCaptcha` fails **closed**: a network error talking to Cloudflare's `siteverify` endpoint is treated as a failed CAPTCHA, not a bypassed one.
  - **Email verification** adds `User.emailVerifiedAt`/`verifyTokenHash`/`verifyTokenExpiresAt`, the same hashed-token-with-expiry shape as password reset (`src/routes/auth.js#issueEmailVerification`, consumed by `POST /auth/verify-email`), just with a 24-hour window instead of reset's 30 minutes since confirming an inbox is real is lower-stakes than authorizing a credential change. A Google sign-in sets `emailVerifiedAt` immediately at creation (or at auto-link time, onto a pre-existing password account) rather than ever going through this flow — Google already required `payload.email_verified` before either path runs. The migration that introduced these columns backfilled every pre-existing row's `emailVerifiedAt` to its own `createdAt`: retroactively locking out accounts that were already in use before verification existed would be a regression, not a security fix, and `prisma/seed.js`'s two dev accounts are seeded pre-verified for the same reason (no real inbox to click a link in locally). An unverified account can otherwise use the app fully — verification only gates `POST /friends/requests` (via `requireVerifiedEmail`, see above), because sending an unsolicited request to a stranger's public ID is the actual bot-abuse vector this exists to close, not anything the account does with people it's already connected to.
- **Friends** (`src/routes/friends.js`, mounted at `/api/friends`, `User.publicId` + `Friendship`): you must be mutual, accepted friends before you can message someone at all. `User.publicId` is a short random code (`src/lib/publicId.js`, alphabet excludes `0/O/1/I/L`), generated once at signup and handed out instead of the numeric `id` specifically because the numeric id is sequential and enumerable (id=5 existing tells you id=1..4 probably do too) — a public "add me" code must not leak that. `Friendship` reuses `Conversation`'s canonical-pair trick (`userAId = min`, `userBId = max`, `@@unique([userAId, userBId])`) so there's one row per pair regardless of who acts first, plus a `status` (`pending`/`accepted`/`declined` never persists — see below — /`blocked`) and a `requestedById` recording who actually initiated (the one thing the canonical pair alone can't tell you). A **mutual request auto-accepts**: if B requests A while A's request to B is still pending, `POST /friends/requests` flips straight to `accepted` instead of leaving two pending rows each side has to separately act on — this mirrors how "you both hit add" behaves in most consumer apps. Declining or cancelling a request **deletes the row** rather than storing `declined`, on purpose, so the same two people can try again later without a stale row in the way; only `blocked` persists (it's an upsert to the same canonical row, so blocking overwrites any prior pending/accepted state, and only the user who set it can clear it via `POST /:userId/unblock`). `src/routes/chat.js` imports `areFriends()` from here and checks it both at `POST /conversations` (403 if not friends) and again at `POST /conversations/:id/messages` (re-checked at send time, not just conversation-creation time, so unfriending after the fact blocks new sends but old history stays readable) — deliberately not checked on the read routes. The old `GET /chat/users?q=` fuzzy directory search (find anyone by typing part of their name/email) was removed entirely rather than kept alongside this: once signup is public, letting any account browse every other registered user by name is the same privacy problem the public/numeric-id split above exists to avoid. `GET /friends/lookup?publicId=` is the only way to find someone now, and only by the exact code they handed you.
- **PWA + Web Push** (`web/public/manifest.webmanifest`, `web/public/sw.js`, `web/public/icons/`, `src/routes/push.js` mounted at `/api/push`, `src/lib/push.js`, `PushSubscription`): `web/src/main.jsx` registers the service worker unconditionally on load, which is what makes the app installable — that part needs no permission and no login. Actually *subscribing* to push is separate and gated behind an explicit user gesture on the Account page (`web/src/hooks/usePushSubscription.js`), because `Notification.requestPermission()` must be called from one. VAPID keys are self-generated (`npx web-push generate-vapid-keys`, no external account) and optional at the `src/lib/email.js`/Resend pattern: `src/lib/push.js#sendPushToUser` no-ops (logged, not thrown) if `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` aren't set, so the app runs fine with push simply unavailable. A subscription is per-browser (`endpoint` is globally unique, upserted on re-subscribe), so one account can have several. `POST /chat/conversations/:id/messages` fires a push at the recipient **only when `chatBus.hasSubscribers(otherUserId)` is false** — someone with a live SSE stream open already gets the message that way, and pushing them too would be a redundant OS notification for the same event; this also means the "who's connected" check `chatBus.js` gained (`hasSubscribers`, a thin wrapper over `EventEmitter#listenerCount`) inherits its single-process caveat — on more than one instance it only sees this process's subscribers. The push call is fired without `await`ing it (`.then(...).catch(console.error)`), because a slow or failing push must never delay the response the sender is waiting on. `sendPushToUser` deletes a subscription outright on a `404`/`410` from the push service (the browser itself revoked it) but leaves it alone and just logs on any other error, so a transient failure doesn't lose a working subscription. Friend-request notifications (`src/routes/friends.js#notify`) are simpler but *not* symmetric with chat's gating: they fire unconditionally rather than checking `chatBus.hasSubscribers`, because that would only tell you the recipient has a *chat* stream open, not that they've seen the request — push and the live "friend" SSE event below are two independent signals, not one gating the other. **iOS note**: Safari only supports Web Push for a PWA actually added to the Home Screen (16.4+); granting permission from a normal Safari tab does nothing there.
- **Google sign-in** (`src/routes/auth.js`, `GET /auth/google` + `/auth/google/callback` + `POST /auth/google/exchange`) is the Authorization Code flow via `google-auth-library`'s `OAuth2Client`, and it's optional the same way `src/lib/email.js`/`src/lib/push.js` are: a module-level `googleConfigured = Boolean(GOOGLE_CLIENT_ID && GOOGLE_CLIENT_SECRET && GOOGLE_REDIRECT_URI)` gate makes `GET /auth/google` `503` cleanly instead of constructing a client with `undefined` credentials, so the app runs fine with Google sign-in simply unavailable. CSRF protection is a `state` value round-tripped through an httpOnly, `sameSite=lax` cookie (`g_oauth_state`, 5-minute TTL) rather than server-side session storage, since this app has no session store at all — bearer JWT only. Handing the browser a real JWT after Google's redirect reuses the **exact same single-use-ticket pattern** as the SSE stream's `POST /stream-ticket` (a `Map` of random-ticket → payload, 30-second TTL, consumed exactly once): a full-page redirect can't receive a JSON response, and a JWT sitting in a URL would leak into access logs, browser history, and `Referer` headers, so `GET /auth/google/callback` mints a short-lived ticket, redirects to `${APP_URL}/oauth-callback?ticket=`, and `POST /auth/google/exchange` trades it for the real `{ token, user }` — mirroring the stream ticket's reasoning exactly rather than inventing a second pattern for the same problem. Sign-in resolves to a user by `googleId` (Google's stable `sub` claim) first; if that misses but a `User` row already exists with the same **Google-verified** (`email_verified: true`) email, it auto-links by setting `googleId` on that row rather than creating a second account — one person should get one account regardless of which method they used to sign in, and only a Google-*verified* email is trusted enough to link onto an existing password account. `User.passwordHash` is nullable for exactly this reason (a Google-only account never sets one); `POST /auth/login` and `PATCH /auth/password` both check for `null` before calling `bcrypt.compare` (which throws on a null comparand) and return a clear "this account signs in with Google" error instead of a 500. Every failure path (`invalid_state`, `email_not_verified`, `google_exchange_failed`, `google_not_configured`) redirects to `${APP_URL}/login?error=<reason>` rather than rendering an error page server-side, keeping the SPA in control of all UI.
- **Live friend-request updates** reuse chat's existing SSE connection rather than a second stream/ticket system: `src/routes/friends.js#publishFriendEvent(userId, type)` calls `chatBus.publish(userId, "friend", { type })` at the same three trigger points that already fire a push notification (a new request landing, a direct accept, and the mutual-auto-accept case), and `GET /api/chat/stream` needed no changes at all to carry it — it already forwards *any* event name a subscriber publishes (`res.write(`event: ${event}\n...`)`), it just happened to only ever see `"message"` before. On the frontend, `web/src/context/ChatContext.jsx` (which owns the one `EventSource` per session) adds a second `es.addEventListener('friend', ...)` alongside its existing `'message'` one and exposes `subscribeToFriendEvents(callback)` the same shape as `subscribeToConversation`; `FriendsProvider` (nested inside `ChatProvider` in `App.jsx` for exactly this reason) calls `useChat()` to get it and just re-runs its existing `refresh()` on any event rather than trying to patch state from the bare `{ type }` payload — a full refetch is cheap and it's the same source of truth the mount-time fetch already trusts. Declining/cancelling a request deliberately publishes nothing, matching `notify()`'s existing no-push behavior for those actions. Inherits the same single-instance caveat as the rest of `chatBus.js`.
- **Profile fields, presence, and per-device push** (`src/lib/publicUser.js`, `User.statusMessage`/`avatarKey`, `PushSubscription.userAgent`) are four small features sharing one idea: everything another user sees about you goes through a single shape. `PUBLIC_USER_SELECT` + `toPublicUser()` in `src/lib/publicUser.js` are what `chat.js` and `friends.js` both select and render through, so adding a profile field means touching one file rather than remembering every route that embeds a user — and `toPublicUser` is what swaps the stored `avatarKey` for a short-lived presigned `avatarUrl`, so the raw key never leaves the server and no permanent avatar URL exists (same reasoning as message attachments). `statusMessage` is capped at 80 characters and normalises blank to null, so readers have one "unset" state rather than two. `PATCH /users/me` handles each field only when it's actually present in the body: `publicId` is a one-shot change guarded by `publicIdCustomized` while `statusMessage` is freely editable, and a single shared guard at the top of that handler (what it used to have) meant a status-only update 409'd forever once the custom ID was spent. Avatars reuse the attachments R2 pipeline but under an `avatars/<userId>/` prefix, never `conversations/` — that keeps `POST /chat/.../messages`'s "attachment must start with `conversations/<this id>/`" check unable to be satisfied by an avatar object, and `PUT /users/me/avatar` re-checks the returned key against the caller's own prefix *and* re-reads the object's real type off R2, because the key round-trips through the client. `isOnline` is a point-in-time `chatBus.hasSubscribers()` read answered at fetch time, deliberately not its own SSE event: a presence broadcast means fanning every connect/disconnect out to everyone who's friends with that user, which is a lot of traffic for a dot — it inherits the same single-process caveat as the rest of `chatBus`. `PushSubscription.userAgent` exists only so `GET /push/subscriptions` can label rows well enough to revoke the right one; that route never returns the `endpoint` or `p256dh`/`authKey` (those are the credentials for pushing to that browser), and `DELETE /push/subscriptions/:id` scopes by `userId` so someone else's id is a 404, never a successful delete. This is the one way to revoke a device you no longer have — `POST /push/unsubscribe` can only ever act on the browser making the call.
- **Link previews** (`src/lib/safeFetch.js`, `src/lib/linkPreview.js`, `LinkPreview` + `Message.linkPreviewId`) unfurl the first URL in a message body. The whole risk of the feature is that the server makes an outbound request to a URL a third party chose, so `safeFetch.js` is built on `node:http`/`node:https` `request()` rather than `fetch()` for one specific reason: `request()` accepts a `lookup` option, and guarding *that* means the socket connects to an address already validated. The obvious alternative — resolve the hostname, check it, then `fetch(url)` — is wrong, because between the check and the fetch the attacker's nameserver can answer again with `127.0.0.1`; guarding `lookup` closes that window rather than narrowing it. Redirects are followed by hand (max 3) so **each hop re-runs the full check** — a 302 to `169.254.169.254` is the entire attack. The blocklist unwraps IPv4-mapped IPv6 (`::ffff:127.0.0.1`) before checking, which is the most commonly missed bypass. Any new server-side outbound fetch should go through `safeGet` rather than calling `fetch()` directly. Thumbnails are **downloaded and stored as Postgres `bytea`, never hotlinked**: `src/app.js` pins `img-src 'self'`, and widening it would leak every *reading* user's IP to whatever host the *sender* chose. Because that image route sits behind the JWT middleware and an `<img>` can't send an `Authorization` header — the same constraint that put `EventSource` on the stream-ticket pattern — the frontend fetches the bytes with the token and renders a `blob:` URL (`fetchLinkPreviewImage` in `web/src/api/chat.js`); reuse that rather than adding a second ticket system or loosening the CSP. An HTML fetch **truncates** at its size cap and parses what arrived (plenty of ordinary sites ship over 512KB, and rejecting them lost the preview entirely), while an image fetch rejects — half a PNG is not a smaller PNG. Previews are never refetched (a snapshot of what the link looked like when shared is the right semantics for a chat log) and failures are cached as their own row so a dead link costs one fetch, not one per share.
- **Disappearing messages** (`Conversation.disappearingSeconds`, `Message.expiresAt`, `src/lib/messageExpiry.js`) put a conversation on a timer. The duration is read **exactly once**, at send time, to stamp an absolute `expiresAt` — which is what makes changing the timer non-retroactive for free, and lets a sender know a message's lifetime at the moment they send it. Either participant may change it (unlike mute, which is per-side), so the change is published to both as `disappearing-changed`. The sweep hard-deletes and publishes `message-expired`, a **distinct event from `message-deleted`**: deleted keeps the bubble and shows a tombstone, expired removes it entirely. Its cron in `src/server.js` runs unconditionally (no `driveConfigured`-style gate to sit behind, since Drive backup doesn't exist in this app) — the timer is a promise to both participants, not an optional integration.
- Money/Decimal handling, S3-compatible upload storage, audit logging, VAT/tax, cash-shift reconciliation, and role-based access do **not** exist in this app — they were part of the shop app this was split from and were deliberately not carried over. If you're tempted to add one of these because it "seems missing," check the Roadmap below first; it's very likely out of scope rather than forgotten.

## Roadmap (not yet implemented)

These are planned next phases, mentioned here so their absence isn't mistaken for an oversight:

1. **A `role`/permission field on `User`.** Not needed yet — every account can do the same things in this app — but if any admin-style capability is ever added, it should be scoped to "what can this account do in *this* app," not resurrect the old shop app's admin/staff distinction.

## Conventions

- Backend and frontend are separate npm projects (root `package.json` vs `web/package.json`) with independent dependencies and CI jobs.
- Never commit `.env` (gitignored) — use `.env.example` as the template for required environment variables.
- New backend routes needing role restriction should reuse `requireRole` rather than checking `req.user.role` ad hoc, once a role field actually exists again (see Roadmap).
